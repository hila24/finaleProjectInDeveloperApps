# בדיקות כללי האבטחה

55 בדיקות על `firestore.rules`, שרצות מול אמולטור Firestore מקומי.

האמולטור טוען את **אותו קובץ** `firestore.rules` שנפרס לפרויקט האמיתי, ולכן מה
שהבדיקות מוכיחות הוא בדיוק מה שקורה בייצור. הן לא נוגעות ב‑`snapvote-hila-2026`,
לא יוצרות משתמשים אמיתיים, ולא עולות כלום.

## הרצה

```bash
npm install                 # פעם אחת בלבד

cd ..
firebase emulators:exec --only firestore --project demo-snapvote \
  "cd firestore-tests && node --test tests/"
```

צריך `firebase-tools` ו‑Java. מזהה הפרויקט `demo-snapvote` הוא מזהה מיוחד שאומר
ל‑Firebase שמדובר באמולטור בלבד, כך שאין צורך בהתחברות.

## מה יש בכל קובץ

| קובץ | קבוצה | בדיקות |
|---|---|---|
| `tests/flow.test.mjs` | זרימה מלאה — הרשמה, ייחודיות שם, תנאי יצירת סקר, הצבעה כפולה | 14 |
| `tests/friends.test.mjs` | חברים — חברות הדדית, פרטיות הפיד, שאילתה פתוחה מול מסוננת | 14 |
| `tests/counters.test.mjs` | ספירת ההצבעות — קול אחד בכל פעם, חסימה אחרי הדדליין | 11 |
| `tests/comments.test.mjs` | תגובות — התחזות, טקסט ריק, אורך מקסימלי, מחיקה | 9 |
| `tests/voters.test.mjs` | מי הצביע — מי רשאית לקרוא את ההצבעות | 7 |

`tests/helpers.mjs` בונה את הנתונים לכל בדיקה: בעלת סקר, חברה, זרה, סקר פתוח,
סקר סגור וסקר שאסור לראות.

## שתי נקודות ששווה להכיר

**כל קובץ מקבל מזהה פרויקט משלו** (`demo-snapvote-flow`, `demo-snapvote-friends`…).
`node --test` מריץ כל קובץ בתהליך נפרד ובמקביל, ובלי הפרדה כזו `clearFirestore()`
של קבוצה אחת היה מוחק את הנתונים של קבוצה אחרת באמצע ריצה.

**שתי בדיקות ב‑`counters.test.mjs` משחזרות את הטרנזקציה האמיתית** של
`PollRepository.castVote`, בשני מצבי ההצבעה. הן שם כדי שהכללים ייבדקו מול מסלול
הכתיבה שהאפליקציה באמת מבצעת, ולא מול קירוב שלו — אחרת קל להדק כלל בטעות עד
שהאפליקציה עצמה נחסמת.
